### The `encryption_key` finding

`bench restore` restores the database and the files. It does not copy `encryption_key` into the new site's `site_config.json`. The drill showed what happens:

1. Before the key copy, `self_service.view` for a valid source manage token returned `valid: false`, "This link no longer works...".
2. That call made Frappe generate a new `encryption_key` and write it to the drill `site_config.json`, with no warning.
3. After the original key replaced it, the same token was valid and all encrypted fields decrypted.

Manage links are HMAC-signed with `encryption_key`, and Password fields (Chapa keys, Email Account password, SMS token) are encrypted with it. A restore must put the original key back before the site serves any request. The `*-site_config_backup.json` file next to each backup has the key. Keep it in the secret store, not only next to the backups. The runbook restore steps say this.

## Defects found

These are reported for the app owners. The drill did not change app code.

### D1: The newsletter campaign job is never scheduled

`appointment/hooks.py` has two `"cron"` keys in the `scheduler_events` dict (lines 244 and 255). Python keeps only the second one, so `appointment.content.newsletter.campaigns.run_due` (`* * * * *`) is lost.

Evidence: the readiness report says `Scheduled jobs missing: appointment.content.newsletter.campaigns.run_due`. No Scheduled Job Type row exists for that method, on the fresh drill site after two migrates and on the development site.

Fix: merge the two `cron` dicts into one.

### D2: A fresh install has no Amharic translations

The Amharic catalog is imported only by patches (`appointment.patches.v0_1.import_*_translations`). `bench new-site` and `install-app` mark all patches as done without running them. So a new site has 0 Amharic Translation rows. The development site, which ran the patches, has 3,259. `migrate` does not fix it.

Evidence: the readiness report on the drill site says "Amharic covers 0 of 3258 catalog strings". `frappe.db.count("Translation", {"language": "am"})` gives 0 on the drill site.

Fix: run the catalog import from `after_install` too (or from an idempotent `after_migrate` hook), not only from patches. This affects the production install, which will be a new site.

### D3: Owner onboarding makes two Provider records for one user

The frontend calls `onboarding.set_onboarding_type("organization")` and then `scheduler.workspace.create`. The first call inserts a Provider ("Hanna Bekele", `onboarding_type` organization). The second call inserts another Provider for the same user ("Lumen Family Clinic — Hanna Bekele", with an empty `full_name`), and links only that one to the business.

The second record has no `full_name`, so `workspace.overview` and the `create` answer return `provider_name: null`.

Evidence: on the drill site, `frappe.get_all("Provider", {"user": owner})` returns two rows. The same happened on the development site (see the incident below).

Fix: let `workspace.create` reuse the Provider that `set_onboarding_type` made, or set `full_name` and stop the duplicate.

### Smaller observations

- `public_experience.api.get_public_experience_snapshot` returns HTTP 500 (`PublicResolutionError`) for a path that is not a public site path, for example `/schedule/org/<slug>`. The development site does the same. A 404 is the expected answer.
- The development site had a pending patch (`import_walkin_hours_translations`). The restored site ran it during `migrate` with no error. Run `migrate` on the development site.
- The readiness report fails `encryption_key` on a fresh site because Frappe makes the key only at first use. This is correct for production, where the key must come from the secret store.
